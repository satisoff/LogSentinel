## 2. The Core Problem We Are Solving

Modern software systems change continuously through:

- Code deployments and application updates.
- Configuration changes.
- Feature-flag updates.
- Dependency upgrades.
- Infrastructure modifications.
- Workload changes and other operational events.

Existing anomaly detectors monitor telemetry such as latency, CPU utilization, error rates, memory consumption, and logs. They identify behavior that deviates from a learned baseline or expected pattern.

However, **a deviation from previous behavior does not automatically mean that something is wrong**.

For example, imagine that a service usually responds in 100 milliseconds. After a deployment, its response time increases to 120 milliseconds.

A conventional anomaly detector might flag the increase because it differs from historical behavior. But several explanations are possible:

1. The deployment introduced a genuine performance regression.
2. The application intentionally changed its behavior.
3. The increase is a short-lived adaptation during rollout.
4. A temporary infrastructure issue caused the increase.
5. The increase has no meaningful effect on users or service reliability.

These cases should not necessarily result in the same operational response.

The fundamental problem is that anomaly detection and deciding whether an anomaly deserves action are two different tasks.

We want to investigate whether adding an operational qualification layer can help distinguish harmless deviations from genuinely harmful regressions.

### Our central research question

Can an actionability-aware, change-conditioned framework distinguish benign post-change behavioral deviations from operationally significant regressions while reducing false alerts and unnecessary operational actions compared with existing approaches?

---

## 3. What LogSentinel Actually Does

LogSentinel is a proposed system that qualifies anomalous behavior observed after a software or configuration change.

Think of it as two connected layers.

### Layer 1: Anomaly detection and behavioral analysis

This layer observes the system and identifies deviations or unusual behavior using telemetry such as:

- Request latency and error rate.
- CPU and memory utilization.
- Request volume and traffic patterns.
- Database latency and connection-pool usage.
- Timeout, retry, and exception counts.
- New log templates and error categories.

It also uses the change event and pre-change baseline to estimate what behavior would reasonably be expected after the change.

### Layer 2: Operational qualification — our main research focus

This layer examines the anomaly evidence alongside change context, persistence, uncertainty, and service impact.

It asks:

- What changed in the software or its environment?
- Is the observed deviation unexpected given that change?
- Does it disappear quickly or persist over time?
- Is it getting worse?
- Are users or service-level objectives affected?
- Does the evidence justify an operational action?

The output is not merely an anomaly score. It is an operational qualification class and a recommended response.

**The primary goal is not to reduce the number of anomalies that exist. It is to reduce unnecessary actions on detected anomalies without missing important regressions.**

For example, the system may identify ten unusual episodes, but only three may warrant investigation or escalation. This is an illustrative example, not an expected or measured result. We must establish the actual numbers experimentally.

Also, the qualification layer must not simply suppress alerts because they occurred near a deployment. A harmful deployment regression is exactly the type of event we need to detect.

---

## 4. The Four Operational Classes

Every post-change episode should eventually receive one of four primary labels.

**BA — Benign Adaptation**

The observed deviation is expected given the change or has negligible service impact.

Recommended response: No action.

**TA — Transient Anomaly**

An unexpected deviation occurs but is short-lived and operationally immaterial.

Recommended response: Observe or continue monitoring.

**AR — Actionable Regression**

The deviation persists or recurs and produces material service-level degradation.

Recommended response: Investigate.

**CR — Critical Regression**

The deviation crosses a predefined severe-impact threshold.

Recommended response: Escalate immediately and consider rollback according to an explicit operational policy.

These labels need formal definitions based on measurable criteria. We should not classify episodes using subjective intuition alone.

For example, the labeling specification should define relevant thresholds, observation windows, persistence conditions, SLO impact, and the severity conditions separating AR from CR.

The four classes are an experimental taxonomy, not a replacement for every organization's incident classification system.

Important: benign behavior is not necessarily an anomaly in the conventional sense. If the input consists of previously detected anomalies, we need to define how BA represents an expected deviation that the underlying detector flagged. Alternatively, our pipeline can qualify broader post-change episodes, including episodes that never cross an anomaly detector's threshold. Analyze this design decision before implementation.

## 5. What Is Different From Existing Research?

Our initial research draft identifies several closely related approaches:

- **MELODY:** Deployment-level anomaly detection using multivariate telemetry, online feature extraction, and semi-supervised/hybrid modeling, with a production AutoRollback setting.
- **SCWarn:** Multimodal detection of bad software changes using heterogeneous data and interpretable alerts.
- Persistence-based anomaly suppression: reducing false alerts caused by short-lived anomalies.
- Conventional context-blind statistical and ML anomaly detectors.
- Cost-aware and SLO-aware alerting approaches.

We must treat these as serious competing approaches or baselines, particularly MELODY and SCWarn.

We must NOT claim that LogSentinel is the first system to use change context, multimodal telemetry, deployment-level anomaly detection, persistence, SLO-aware alerting, or automated rollback.

Our current hypothesis is narrower:

**The potentially differentiated contribution is explicitly formulating and evaluating post-change operational qualification as a joint decision over change-conditioned behavioral deviation, temporal persistence, and measurable service impact.**

We aim to determine whether integrating these elements into an explicit qualification objective provides additional operational value beyond existing change-aware detectors and persistence filters.

This is a hypothesis to investigate, not a proven novelty claim.

Before committing to the final design, examine the relevant literature and compare our proposal with MELODY and SCWarn at the methodology and evaluation levels. Identify which differences are genuine, which are already covered by prior work, and what evidence would be necessary to justify the contribution.

## 6. How We Intend to Build the System

The proposed pipeline is:

1. Capture a software or configuration change.
2. Build a change episode.
3. Collect the pre-change baseline and post-change telemetry.
4. Estimate expected post-change behavior conditioned on the change and workload.
5. Calculate behavioral deviations and their uncertainty.
6. Extract and fuse log and metric evidence.
7. Track persistence, recurrence, severity, and recovery.
8. Measure service impact using SLOs, error-budget burn, and affected-request fraction where available.
9. Qualify the episode.
10. Recommend an operational response and record the evidence supporting it.

The architecture should keep anomaly evidence, qualification decisions, and operational actions separate. This lets us determine which components actually provide value.

Do not begin with automatic rollback. Initially, LogSentinel should recommend actions and record decisions. Any future automated remediation must be separately evaluated and protected by explicit safety policies.

## 7. Which Model or Algorithm Should We Use?

We have not yet established that one particular algorithm is optimal. Select the approach based on the available data, research objectives, interpretability, and experimental results.

Our initial implementation should be practical rather than unnecessarily complex.

### A. Expected-behavior model

Estimate what post-change behavior should look like given:

- The pre-change baseline.
- Change type, service, version, and rollout information.
- Current workload and relevant operating conditions.

Start with a transparent statistical or tree-based approach. Consider more complex sequence models only if the dataset and results justify them.

### B. Behavioral-deviation features

Compare observed telemetry with its expected values or expected ranges.

Retain uncertainty where possible. A small deviation within an appropriate prediction interval should not be treated identically to a substantial deviation outside that interval.

### C. Qualification model

This is the component that learns to classify episodes into BA, TA, AR, or CR.

A plausible initial supervised approach is a tree-based classifier such as XGBoost or another suitable model, depending on the environment and dataset size. Compare it with a transparent rule-based policy.

Potential input features include:

- Change type, scope, version, and rollout percentage.
- Metric deviations and prediction uncertainty.
- Error-rate and latency changes.
- Log severity counts, retries, timeouts, exceptions, and new log templates.
- Duration of abnormal behavior.
- Recurrence and cumulative severity.
- Deviation slope and recovery behavior.
- Affected-request fraction.
- SLO violations and error-budget burn.

The training labels must be derived from controlled experiments and predefined operational criteria. The model should learn from labeled examples rather than relying on hand-written assumptions disguised as learned intelligence.

### D. Operational action policy

Translate the qualification output into a recommendation:

- BA → No action.
- TA → Observe.
- AR → Investigate.
- CR → Escalate or consider rollback.

The action policy must account for the different costs of false alerts, missed regressions, and unnecessary rollback.

Calibrate probability thresholds and action thresholds on the development/validation data. Freeze them before final testing.

Do not assume that the classifier alone constitutes the whole system. The model, feature extraction, uncertainty handling, qualification policy, and output explanation must work together.

## 8. How We Will Train the Qualification Model

The dataset is a critical part of this project.

We intend to build a small, controlled distributed application where we know what changes we make and can observe their consequences.

A possible experimental application contains:

- An API gateway.
- Two or more application services.
- A database.
- A configurable workload/load generator.
- Instrumentation that captures logs and metrics.
- Optional distributed traces where feasible.

Use appropriate observability tooling, such as OpenTelemetry, if it fits the implementation.

For each controlled change, create a dataset episode containing:

1. A pre-change baseline.
2. Structured change metadata.
3. Aligned post-change logs and metrics.
4. Workload and relevant environmental conditions.
5. Observed deviations and persistence information.
6. Measured service impact.
7. A documented ground-truth label and supporting evidence.

A candidate starting design in the research draft is a 30-minute pre-change window and a 30-minute post-change observation window. Treat these as initial experimental choices, validate them in pilot runs, and perform sensitivity analysis rather than assuming that they are universally optimal.

### Controlled scenarios to implement

Include a reasonable range of scenarios drawn from the proposed research design:

- Harmless deployment or refactor.
- Workload increase without a software fault.
- Short-lived database slowdown.
- Inefficient-query deployment that causes sustained degradation.
- Delayed memory leak.
- Infrastructure failure occurring after a deployment but unrelated to it.
- Legitimate new log template following a change.
- Severe error-rate or latency increase.

Each scenario should have a documented purpose, setup, expected behavior, impact criteria, and ground-truth labeling procedure.

Use controlled fault injection and predefined service-impact conditions wherever possible. Expert review can help adjudicate ambiguous episodes; measure reviewer disagreement rather than pretending all labels are perfectly certain.

The initial research draft proposes approximately 100–200 independent episodes as a planning target, not a guaranteed sufficient sample size. Begin with pilot experiments, estimate the feasibility and statistical requirements, and expand or repeat experiments as needed.

### Avoid data leakage

Split training, validation, and test data by independent change episode or change identity—not randomly by individual telemetry rows.

Otherwise, adjacent windows from the same deployment can appear in both training and testing, producing misleadingly good results.

Document the dataset schema, split strategy, label distribution, scenario distribution, and any class imbalance.

## 10. How We Will Measure Success

Our primary objective is **reducing false alerts and unnecessary operational actions while retaining timely detection of harmful regressions**.

Do not evaluate success through accuracy or F1 alone.

Prioritize:

- False alerts per change episode at a fixed recall or predefined alert budget.
- Precision and recall for harmful regressions.
- Detection delay.
- Lead time before SLO violations.
- Unnecessary rollback rate.
- Probability calibration.
- Error-budget burn avoided, where it can be measured credibly.
- Action-weighted operational utility.
- Performance on unseen changes and different workload conditions.

Define how an alert is counted, what qualifies as a missed regression, and what constitutes an unnecessary action before evaluating the final test set.

For example, a system that suppresses nearly every alert may have a low false-alert count but would be useless if it also misses serious regressions. The evaluation must account for this trade-off.

Use episode-level confidence intervals and appropriate repeated experiments. Perform sensitivity analysis on the costs assigned to false alerts, missed regressions, unnecessary rollbacks, and prevented degradation.

The key result we want to investigate is whether LogSentinel can achieve fewer unnecessary actions at comparable harmful-regression recall and acceptable detection delay.

**Do not fabricate results or state that LogSentinel outperforms existing systems until the experiments establish this. Negative results must be reported honestly.**

- Do not build an unnecessarily complex deep-learning model before establishing simple, credible baselines.
- Do not generate arbitrary synthetic labels without a documented causal scenario and labeling rule.
- Do not treat correlation with a deployment as proof that the deployment caused an incident.
